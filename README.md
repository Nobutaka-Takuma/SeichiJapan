# 聖地日本 — みんなで作る、小説とアニメの地図帳

小説やアニメに出てくる場所を地図の上に集め、その場所についての知識を
**Wikipediaのように誰でも書き足せる** 地図帳です。

どこがどのシーンの場所かは、たいていファンの間ではもう分かっています。
足りないのは、それが一箇所にまとまっていないこと。だからこのサービスの中心は
**場所ごとの項目**であり、議論ではありません。

```
由比ヶ浜                                    ♥ 35   [編集] [履歴]
神奈川県 鎌倉市由比ガ浜
登場する作品 1 ・ シーン 1 ・ 編集 2回/2人      最終更新 古地図倶楽部

  ■ 明治期の海水浴場
  明治中期以降、鎌倉は東京からの避暑地として整備が進み……

  行き方・訪問時の注意
  江ノ島電鉄「由比ヶ浜駅」から徒歩5分。夏季は大変混雑します。

  ここが登場する作品・シーン
  ┌────────────────────────┐
  │ [シーンの画像]              │
  │ 小説『こころ』夏目漱石       │
  │ 「私が先生と知り合になった   │
  │  のは鎌倉である。」          │
  └────────────────────────┘
```

## できること

| | |
| --- | --- |
| **場所の項目を共同編集** | 名前・座標・解説・行き方・写真を誰でも編集。全編集が版として履歴に残り、行単位の差分表示と一手での差し戻しができる |
| **シーンの記述も共同編集** | 場面の説明・話数・画像も誰でも直せる。場所と同じく版の履歴と差し戻しつき |
| **地名で地図を移動** | 「新宿区」「沼津市」「秋葉原」などを入れると、その周辺まで一息で飛ぶ。市区町村の索引は登録済みの場所の住所から自動生成しているので、外部接続なしで引ける |
| **地図から直接書き込む** | 地図をクリック →「ここは○○の第3話のあの場面」を登録。近くの既存の場所を候補に出して重複を防ぐ。既存のピンを押せばその場所が選ばれる |
| **作品は予測入力で選ぶ** | 作品数が増える前提で、プルダウンではなく入力で絞り込む。一覧に無ければその場で作品ごと登録できる |
| **画像を添える** | アニメならその場面の画像、小説なら描写にあたるもの。キャプションと出典も記録 |
| **いいね** | 場所に付けられる。多いほど地図のピンが大きくなり、一覧の上に出る |
| **異説** | まれに場所が割れたときだけ、候補を並べて根拠を書き、投票で確度を出す |

### 訪ねるための機能（コンテンツツーリズム）

| | |
| --- | --- |
| **近くの聖地** | 現在地から近い順に、直線距離と徒歩の目安つきで並べる。位置情報を許可しない／使えない場合は地名を入れて同じ画面を引ける |
| **巡礼コース** | 回る順に地点を並べたもの。区間ごとの距離と全体の所要目安を座標から自動計算する。地図アプリへ経由地つきで渡せるので、現地では案内に従うだけで回れる |
| **訪問の記録** | 場所ごとに「行った」を記録。コースの踏破率が進み、ユーザーのページに足跡が残る |
| **地域から探す** | 市区町村ごとに聖地・作品・コース・訪問数を見渡せる。住所から索引を自動生成しているので、迎える側が「うちの町に何があるか」を確認できる |
| **経路を調べる** | 場所ページから地図アプリの経路検索へ直接渡す |

### 読んで迷子になる（回遊）

| | |
| --- | --- |
| **`[[wikilink]]`** | 場所の解説にも、シーンの注記にも書ける。`[[別の場所の名前]]` と書くと項目へのリンクになり、まだ無い項目は赤リンクとして残る |
| **被リンク** | 「この項目に言及している項目」を自動で集めて出す |
| **関連項目** | 同じ作品の別の場所、同じ市区町村の別の作品を辿れる |
| **記述から次の記述へ** | シーンのページから、同じ作品の前後のシーン／同じ場所で描かれた別作品のシーン／その場所の近くで描かれた場所へ飛べる |
| **舞台が重なる作品** | 作品ページから、同じ場所を舞台にしている作品へ。重なっている場所の名前も出す |
| **作品 ⇄ 地域** | 作品ページにその舞台の市区町村、地域ページにその土地を舞台にした作品、場所の住所からその地域へ |
| **おまかせ** | `/random` で場所を、`/random?kind=passage` でシーンを無作為に開く |

どの画面も行き止まりにならないことを目安にしています（収録済みの記述はすべて、
ほかの記述へ 2 本以上の導線を持ちます）。

## 確度について

異説が出ていないシーンでは確度を表示しません（「定説」として扱います）。
複数の候補が並んだときだけ、`src/lib/confidence.ts` で得票シェアを計算します。

```
重み w = max(0, 賛成 − 反対) + 0.5
確度   = w ÷ Σw
```

`+0.5` は票が少ないうちに確度が振り切れないようにするラプラス平滑化です。

## 技術構成

- **Next.js 15（App Router）/ React 19 / TypeScript** — 更新は Server Actions
- **PostgreSQL** — 本番は `DATABASE_URL`（Supabase を想定）。未設定なら
  **PGlite**（PostgreSQL の WASM 版）を `data/pgdata` に置いて使うので、
  手元では何も用意せずに動く。SQL は本物の PostgreSQL 1種類だけ
- **Leaflet + OpenStreetMap** — APIキー不要
- 地名検索は手元のデータ（市区町村の索引＋都道府県表＋登録済みの場所）で完結。
  それでも見つからない地名だけ Nominatim に問い合わせる（サーバ側・1秒間隔・
  結果はキャッシュ。到達できない環境では手元の結果だけで動作）。
  `SEICHI_GEOCODING=off` で外部問い合わせを止められます
- **Tailwind CSS v4**
- **スマートフォン優先**。現地で片手で使う画面なので、下部に固定のタブ（近く／地図／
  聖地／コース／おまかせ）を置き、押せるものは 44px 以上、`viewport-fit=cover` と
  `env(safe-area-inset-bottom)` でノッチ機種に合わせています。横スクロールが出ないことを
  主要画面で確認済み
- 現在地は Geolocation API。距離は緯度経度からの近似（直線距離）で、
  徒歩の目安は分速80mで換算しています
- 認証は scrypt によるパスワードハッシュ＋DBセッション（Cookie）
- 画像は Supabase Storage（未設定なら `data/uploads/`）に保存し、
  `/uploads/[name]` のルートハンドラから配信
  （`public/` は `next start` がビルド時のファイルしか配信しないため使えない）

## 開発

```bash
npm install
npm run dev     # http://localhost:3000
```

初回起動時に `data/pgdata` に PGlite のデータベースが作られ、サンプルデータが
投入されます。作り直したいときは `rm -rf data` してから再起動してください。

```bash
npm run db:setup   # スキーマ作成とデータ投入を明示的に実行（何度流してもよい）
```

### データの追加（データパック）

初期データは **データパック** に分かれていて、起動時に「まだ流していないパック」
だけが適用されます。作品を足すときに DB を作り直す必要はありません。

```
src/lib/data/
  types.ts            パックの型
  apply.ts            適用処理（何度流しても結果が変わらない）
  index.ts            パックの一覧 ← ここに1行足す
  packs/
    initial.ts        0001-initial
    shin-godzilla.ts  0002-shin-godzilla
    routes.ts         0003-routes（巡礼コースの見本）
```

新しい作品を足す手順:

1. `packs/` に `DataPack` を1つ書く（`id` は既存と重複しない連番にする）
2. `index.ts` の `PACKS` に加える
3. `git pull` して再起動するだけ。差分だけが入る

適用済みのパックは `data_packs` テーブルに記録されます。守っていること:

- **利用者が編集した記事は上書きしない。** 同じ名前の場所がすでにあれば、
  その項目には触れず、新しいシーンだけを結びつけます
- 何度実行しても増えない（作品は slug、シーンは本文、比定は組み合わせ、
  票といいねは主キーで重複を防ぐ）
- パックの仕組みを入れる前からある DB は、最初のパックを適用済みとして
  記録してから続きを流します（二重投入されません）

```bash
npm run build && npm start   # 本番ビルド
```

## Vercel + Supabase に公開する

SQLite をやめて PostgreSQL にしてあるのは、Vercel のようなサーバーレス環境では
**ファイルに書いても次のリクエストに残らない**ためです。画像も同じ理由で
Supabase Storage に置きます。

### 1. Supabase 側

1. プロジェクトを作る（リージョンは Tokyo が近い）
2. **Project Settings → Database → Connection string → Transaction pooler**
   の文字列を控える（ポート **6543** のほう。サーバーレスから繋ぐのでこちらを使う）
3. **Storage** で `uploads` という名前のバケットを作り、**Public** にする
4. **Project Settings → API** から `Project URL` と `service_role` キーを控える

### 2. 手元からデータを入れる

```bash
DATABASE_URL='postgresql://...pooler.supabase.com:6543/postgres' npm run db:setup
```

スキーマ作成とサンプルデータの投入がされます。何度実行しても増えません。

### 3. Vercel 側

GitHub リポジトリを Import し、環境変数を設定して Deploy するだけです
（ビルド設定は既定のままで動きます）。

| 変数 | 値 |
| --- | --- |
| `DATABASE_URL` | 手順1で控えた接続文字列 |
| `SUPABASE_URL` | Project URL |
| `SUPABASE_SERVICE_ROLE_KEY` | service_role キー（**公開しないこと**） |
| `SUPABASE_STORAGE_BUCKET` | `uploads` |
| `SEICHI_CONTACT` | 任意。地名検索で外部に名乗る連絡先 |

`.env.example` に同じものを並べてあります。

### 補足

- 手順2を飛ばしても、最初のアクセス時にアプリ自身がスキーマとデータを作ります
  （`pg_advisory_xact_lock` を取るので、同時に複数のインスタンスが起動しても
  二重には入りません）。ただし最初の1リクエストが遅くなるので、
  先に流しておくことを勧めます
- `service_role` キーはサーバー側でしか使いません。`NEXT_PUBLIC_` を付けないこと
- 作品を足したときは、`npm run db:setup` を本番の `DATABASE_URL` に対して
  もう一度流せば、差分だけが入ります

## データモデル

```
PostgreSQL

places（場所＝項目）
  ├ place_revisions（版の履歴）      … 編集のたびに編集後の状態を1件積む
  ├ place_likes（いいね）
  ├ visits（訪問の記録）             … 1人1場所1件。踏破率と足跡の元
  ├ route_stops（コースの停留点）─→ routes（巡礼コース）
  └ identifications（結びつけ）
       ├─ passages（シーン）→ works（作品）   画像・キャプション・出典を持つ
       │    └ passage_revisions（版の履歴）   … シーンも共同編集できる
       ├─ votes（賛成・反対）                 … 異説が出たときだけ効く
       └─ comments（議論）
```

区間距離・所要・踏破率は保存せず、停留点の座標と `visits` から毎回求めています
（場所の座標が直れば、コースの距離もひとりでに直る）。

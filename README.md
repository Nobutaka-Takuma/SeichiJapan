# 聖地日本 — みんなで作る、小説とアニメの地図帳

小説やアニメに出てくる場所を地図の上に集め、その場所についての知識を
**Wikipediaのように誰でも書き足せる** 地図帳です。

どこがどのシーンの場所かは、たいていファンの間ではもう分かっています。
足りないのは、それが一箇所にまとまっていないこと。だからこのサービスの中心は
**場所ごとの項目**であり、議論ではありません。

```
由比ヶ浜                                    ♥ 35   [編集] [履歴]
神奈川県 鎌倉市由比ガ浜
登場する作品 1 ・ シーン 1 ・ 編集 2回/2人      最終更新 古地図倶楽部

  ■ 明治期の海水浴場
  明治中期以降、鎌倉は東京からの避暑地として整備が進み……

  行き方・訪問時の注意
  江ノ島電鉄「由比ヶ浜駅」から徒歩5分。夏季は大変混雑します。

  ここが登場する作品・シーン
  ┌────────────────────────┐
  │ [シーンの画像]              │
  │ 小説『こころ』夏目漱石       │
  │ 「私が先生と知り合になった   │
  │  のは鎌倉である。」          │
  └────────────────────────┘
```

## できること

| | |
| --- | --- |
| **ログインなしで編集** | 編集・シーンの登録・議論への書き込みに、アカウントは要らない。名乗らずに書いた分は「匿名 a3f2」として記録され、あとでアカウントを作れば**そのまま引き継がれる** |
| **場所の項目を共同編集** | 名前・座標・解説・行き方・写真を誰でも編集。全編集が版として履歴に残り、行単位の差分表示と一手での差し戻しができる |
| **シーンの記述も共同編集** | 場面の説明・話数・画像も誰でも直せる。場所と同じく版の履歴と差し戻しつき |
| **地方 → 都道府県 → 地図** | 全国を一枚で出しても点が散らばるだけなので、まず地方、次に県をえらんでから地図を開く。件数が出るので「どこに何があるか」が選ぶ前に分かる |
| **地名で地図を移動** | 「新宿区」「沼津市」「秋葉原」などを入れると、その県の地図へ一息で飛ぶ。市区町村の索引は登録済みの場所の住所から自動生成しているので、外部接続なしで引ける |
| **地図から直接書き込む** | 地図をクリック →「ここは○○の第3話のあの場面」を登録。近くの既存の場所を候補に出して重複を防ぐ。既存のピンを押せばその場所が選ばれる |
| **作品は予測入力で選ぶ** | 作品数が増える前提で、プルダウンではなく入力で絞り込む。一覧に無ければその場で作品ごと登録できる |
| **画像を添える** | 「現地の写真」と「作品からの引用」を区別して扱う。引用は出所を必須にし、枠と「引用」の札を付けて出す |
| **この場面はどこ？** | 手がかりから舞台を地図で当てる遊び。答え合わせから、その場所の項目・作品・行き方へ |
| **いいね** | 場所に付けられる。多いほど地図のピンが大きくなり、一覧の上に出る |
| **異説** | まれに場所が割れたときだけ、候補を並べて根拠を書き、投票で確度を出す |
| **管理者の削除** | 荒らしと権利者からの申し立てのために、管理者だけが項目ごと消せる。消したものは記録に残す |

### 訪ねるための機能（コンテンツツーリズム）

| | |
| --- | --- |
| **近くの聖地** | 現在地から近い順に、直線距離と徒歩の目安つきで並べる。位置情報を許可しない／使えない場合は地名を入れて同じ画面を引ける |
| **巡礼コース** | 回る順に地点を並べたもの。区間ごとの距離と全体の所要目安を座標から自動計算する。地図アプリへ経由地つきで渡せるので、現地では案内に従うだけで回れる |
| **訪問の記録** | 場所ごとに「行った」を記録。コースの踏破率が進み、ユーザーのページに足跡が残る |
| **地域から探す** | 市区町村ごとに聖地・作品・コース・訪問数を見渡せる。住所から索引を自動生成しているので、迎える側が「うちの町に何があるか」を確認できる |
| **経路を調べる** | 場所ページから地図アプリの経路検索へ直接渡す |

### 読んで迷子になる（回遊）

| | |
| --- | --- |
| **`[[wikilink]]`** | 場所の解説にも、シーンの注記にも書ける。`[[別の場所の名前]]` と書くと項目へのリンクになり、まだ無い項目は赤リンクとして残る |
| **被リンク** | 「この項目に言及している項目」を自動で集めて出す |
| **関連項目** | 同じ作品の別の場所、同じ市区町村の別の作品を辿れる |
| **記述から次の記述へ** | シーンのページから、同じ作品の前後のシーン／同じ場所で描かれた別作品のシーン／その場所の近くで描かれた場所へ飛べる |
| **舞台が重なる作品** | 作品ページから、同じ場所を舞台にしている作品へ。重なっている場所の名前も出す |
| **作品 ⇄ 地域** | 作品ページにその舞台の市区町村、地域ページにその土地を舞台にした作品、場所の住所からその地域へ |
| **おまかせ** | `/random` で場所を、`/random?kind=passage` でシーンを無作為に開く |

どの画面も行き止まりにならないことを目安にしています（収録済みの記述はすべて、
ほかの記述へ 2 本以上の導線を持ちます）。

## 地図の出し方

日本全体を一枚の地図で出しても、点が小さく散らばるだけで「どこに何があるか」は
読み取れません。そこで**地方 → 都道府県 → 地図**の順に絞ってから見せています。

- 地方は8地方区分の中部を「北陸・甲信越」と「東海」に割った9つ（`src/lib/regions.ts`）。
  三重県は東海に置いています
- 地方にも県にも**登録件数を出します**。選ぶ前に「どこに何があるか」が分かり、
  0件の県は「まだありません」として残すので、**足りない場所も見えます**
- 行き先が決まっている人には遠回りなので、**地名からの近道**を併せて置いています
  （「秋葉原」→ 東京都の地図）
- 「群馬県／新潟県」のように県をまたぐ場所（清水トンネルなど）は、
  数えるときも絞るときも区切りでばらして、**どちらの県からも出る**ようにしています

## 引用の扱い

作品の一場面を引けると、聖地の魅力はぐっと伝わります。ただし著作物なので、
**引用として成り立つ形**でしか載せられません。そのための仕組みを入口に置いています。

画像には `image_kind`（`site_photo` / `work_quote`）を持たせ、扱いを分けています。

| 引用として要ること | どう担保しているか |
| --- | --- |
| 明瞭区別性（どこからが引用か分かる） | 引用は破線の枠で囲い、「引用」の札を付けて表示（`QuotedImage`） |
| 出所の明示 | 掲載箇所と出典が空なら**保存できない**（`checkQuotation`） |
| 主従関係（説明が主、引用が従） | 引用だけの投稿を弾く。あなた自身の説明が20字以上ないと保存できない |
| 必要な範囲 | 1シーンにつき1点。表示の高さを抑え、拡大リンクを付けない |

`/rights` に、この方針と権利者向けの連絡先をまとめています。
連絡先は環境変数 `SEICHI_CONTACT` から出ます。

## この場面はどこ？（`/guess`）

手がかりを見て地図の上で場所を指し、正解までの距離で採点する遊びです。5問1組。
答え合わせから、その場所の項目・作品・行き方へつながります。

- 採点は `5000 × exp(−距離 / 30km)`。100mでほぼ満点、20kmで2500点台、100kmで200点弱
- 手がかりは **現地の写真 → 場面の記述 → 本文引用** の順に選びます
- 記述に場所名が入っていることが多いので、**名前は伏せ字にして**出します
- **作品からの引用画像は手がかりに使いません。**
  引用は説明の裏づけとして載せるもので、遊びの題材にすると目的から外れるためです
- 答えは画面に出しません。署名した httpOnly の Cookie に隠し、採点はサーバ側で行います
  （手がかりと一緒に答えを送ると、画面を覗くだけで分かってしまうため）

現地の写真が増えるほど面白くなる作りにしてあるので、写真の投稿を促す仕掛けにもなっています。

## ログインが要るもの、要らないもの

**書くことのほとんどに、アカウントは要りません。** 思いついたときに直せることのほうが、
名前が揃っていることより大事だと考えています。

| | ログイン |
| --- | --- |
| 場所の項目の編集・差し戻し | 要らない |
| シーンの登録・編集・差し戻し | 要らない |
| 地図からの書き込み（画像つき） | 要らない |
| 作品の追加・巡礼コースの作成 | 要らない |
| 議論への書き込み・異説の提案 | 要らない |
| **旅の記録**（行った場所・コースの踏破） | **要る** |
| **いいね** | **要る**（1人1回で数えるため） |
| **投票** | **要る**（1人1票で確度を出すため） |

### 匿名の書き手も users の行を持つ

名乗らずに書いた人にも、`users` の行をひとつ作ります（`is_anon = true`）。
こうしておくと、版の履歴・差分・差し戻し・貢献の一覧といった仕組みが、
**ログインした人とまったく同じ経路で動きます**。専用の分岐はどこにも要りません。

- 名前は Cookie の合言葉の SHA-256 から決まります（`anon-a3f21b9c` ／ 表示は「匿名 a3f2」）。
  合言葉そのものは出さないので、名前を見ても他人がなりすますことはできません
- `password_hash` は空で、**この行ではログインできません**
  （`verifyPassword` が必ず false を返し、ログインの問い合わせも `password_hash <> ''` で弾きます）。
  `anon-` を含むIDは登録の形式検査も通りません
- 行を作るのは**入力の検証が通ってから**です。空振りしただけで行が増えることはありません
- 個人を特定する情報（IPアドレスなど）は保存していません

### あとから名乗ると、それまでの分が引き継がれる

匿名で書いた人が登録すると、新しい行を作らず、**匿名の行をそのまま名前のある行に変えます**。
外部キーはすべてその行を指しているので、それまでの編集・投稿・議論がまるごと自分のものになります
（移し替えの処理は要りません）。

### 荒らしへの備え

障壁を下げた分のリスクは、後始末の側で受けます。

- すべての編集が版として残り、**一手で差し戻せます**（差し戻し自体も匿名でできます）
- 差し戻しで直せないものは、管理者が消せます（下記）
- 同じブラウザからの書き込みは同じ名前にまとまるので、荒らしの範囲を追えます

## 管理者と削除

誰でも編集できる場所には、必ず片づけが要ります。宣伝目的の投稿、権利者から
申し立てのあった画像、間違って二重に作られた項目。差し戻しで直せないものは、
管理者が消せるようにしてあります。

### 誰が管理者か

環境変数 `SEICHI_ADMINS`（カンマ区切りのID）で決まります。

```
SEICHI_ADMINS=kobo_map,someone_else
```

**起動のたびに反映されます。** ここから外した人はその場で権限を失うので、
権限の付け外しは環境変数を書き換えて再デプロイするだけで済みます。
**サンプルデータの利用者が既定で管理者になることはありません。**

手元で試すときは、開発サーバを止めてから:

```bash
npm run admin -- 一覧
npm run admin -- 付与 kobo_map
npm run admin -- 剥奪 kobo_map
```

（手元のデータベース（PGlite）は1つのプロセスからしか開けないため、
サーバを動かしたままだと反映されません。）

### 何が起きるか

- 削除は**実体を消します**。表示から隠すだけの論理削除にすると、
  絞り込みを書き忘れた問い合わせが1本でもあれば漏れてしまい、
  権利者からの申し立てに応えられないからです
- かわりに、**消したものは `deletions` に丸ごと控えます**。誰が・何を・なぜ
  消したかと、消した行の中身そのもの。`/admin` で一覧できます
- 取り消しはできません。UIにもそう書いてあります
- 画像は**実体ごと**消します（Supabase Storage / `data/uploads` の両方）

| 消せるもの | 一緒に消えるもの |
| --- | --- |
| 場所の項目 | 結びついた説・版の履歴・いいね・訪問記録・コースの停留点 |
| 記述 | 説・票・コメント・版の履歴・添付画像 |
| 説 | その説に投じられた票 |
| コメント | — |
| 巡礼コース | 停留点の並び（場所そのものは残る） |
| 作品 | その作品の記述すべて（取り違え防止に作品名の入力を求める） |

### 権限の確かめ方

判定は Server Action の中で `requireAdmin()` を通す一箇所だけです。
画面にボタンを出さないのは目隠しにすぎないので、
**同じリクエストを権限のない人が再送しても断られる**ことを確認しています。

## 確度について

異説が出ていないシーンでは確度を表示しません（「定説」として扱います）。
複数の候補が並んだときだけ、`src/lib/confidence.ts` で得票シェアを計算します。

```
重み w = max(0, 賛成 − 反対) + 0.5
確度   = w ÷ Σw
```

`+0.5` は票が少ないうちに確度が振り切れないようにするラプラス平滑化です。

## 技術構成

- **Next.js 15（App Router）/ React 19 / TypeScript** — 更新は Server Actions
- **PostgreSQL** — 本番は `DATABASE_URL`（Supabase を想定）。未設定なら
  **PGlite**（PostgreSQL の WASM 版）を `data/pgdata` に置いて使うので、
  手元では何も用意せずに動く。SQL は本物の PostgreSQL 1種類だけ
- **Leaflet + OpenStreetMap** — APIキー不要
- 地名検索は手元のデータ（市区町村の索引＋都道府県表＋登録済みの場所）で完結。
  それでも見つからない地名だけ Nominatim に問い合わせる（サーバ側・1秒間隔・
  結果はキャッシュ。到達できない環境では手元の結果だけで動作）。
  `SEICHI_GEOCODING=off` で外部問い合わせを止められます
- **Tailwind CSS v4**
- **スマートフォン優先**。現地で片手で使う画面なので、下部に固定のタブ（近く／地図／
  聖地／コース／おまかせ）を置き、押せるものは 44px 以上、`viewport-fit=cover` と
  `env(safe-area-inset-bottom)` でノッチ機種に合わせています。横スクロールが出ないことを
  主要画面で確認済み
- 現在地は Geolocation API。距離は緯度経度からの近似（直線距離）で、
  徒歩の目安は分速80mで換算しています
- 認証は scrypt によるパスワードハッシュ＋DBセッション（Cookie）。
  匿名の書き手は別の Cookie（`seichi_anon`）で見分けます
- 画像は Supabase Storage（未設定なら `data/uploads/`）に保存し、
  `/uploads/[name]` のルートハンドラから配信
  （`public/` は `next start` がビルド時のファイルしか配信しないため使えない）

## 開発

```bash
npm install
npm run dev     # http://localhost:3000
```

初回起動時に `data/pgdata` に PGlite のデータベースが作られ、サンプルデータが
投入されます。作り直したいときは `rm -rf data` してから再起動してください。

```bash
npm run db:setup   # スキーマ作成とデータ投入を明示的に実行（何度流してもよい）
```

### 調査結果の取り込み（別のAIに調べてもらう）

コンテンツを増やすとき、調べる作業は外（別のAIや調査担当）に出せます。
そのときの**渡し方の指示書**が [`docs/調査依頼.md`](docs/調査依頼.md) です。
そのまま渡せる形にしてあります。

要点はひとつ。**相手に緯度経度を書かせない**ことです。

言語モデルは座標を「それらしく」書きますが、数百メートル、ときに市ひとつ分ずれます。
数百メートルずれた座標は、現地に立つ人を迷わせるので無いほうがましです。
そこで指示書では、座標のかわりに**位置の識別子**を求めています。

| 求めるもの | 例 | なぜ |
| --- | --- | --- |
| Wikidata の項目ID | `Q11529113` | P625 から正確な座標を引ける |
| OpenStreetMap の要素 | `way/123456789` | 同上。建物の輪郭まで特定できる |
| 住居表示レベルの住所 | `新宿区須賀町5` | 上の2つが無いときの手がかり |
| `precision` | `point` / `site` / `area` | 「この商店街」を点として扱わないため |
| `lat` / `lng` | 任意 | **照合にしか使わない** |

座標はこちら（`npm run intake`）が識別子から引き直し、
相手が書いてきた座標と食い違えば、その場所を弾きます。

```bash
npm run intake -- research.json                  # 点検だけ
npm run intake -- research.json --write          # 通ったものを packs/ に書き出す
```

点検で見ていること:

| 見ている点 | 判定 |
| --- | --- |
| 座標が日本の範囲外（緯度経度の入れ替わりも検出） | ✗ |
| Wikidata / OSM から引いた座標と食い違う（point 150m / site 400m / area 1500m） | ✗ |
| 位置の根拠（wikidata・osm・address）がひとつも無い | ✗ |
| 私有地・個人宅として申告されている | ✗ |
| 保護期間内の作品を逐語引用している | ✗ |
| 「公式」と書いてあるのに出典が無い | ✗ |
| 座標の桁が粗い（小数第3位以下 ≒ 100m超の誤差） | △ |
| **すでにある項目の120m以内**（別名で二重に作られるのを防ぐ） | △ |
| 出典が無い／広がりのある場所に代表点の説明が無い | △ |

**照合できなかったときは、その旨を必ず出します。** 外部に接続できない環境では
「照合は行われていません」と明記し、確かめないまま「確かめた」ことにはしません。
書き出したパックにも、座標ごとの出どころ（Wikidata から引き直し／未照合）を
コメントで残します。

取り込むのは `.ts` のデータパックです（JSONを直接読み込みません）。
git の履歴に残り、「この場所はいつ、どの調査から入ったのか」を後から追えるようにするためです。

### データの追加（データパック）

初期データは **データパック** に分かれていて、起動時に「まだ流していないパック」
だけが適用されます。作品を足すときに DB を作り直す必要はありません。

```
src/lib/data/
  types.ts            パックの型
  apply.ts            適用処理（何度流しても結果が変わらない）
  index.ts            パックの一覧 ← ここに1行足す
  packs/
    initial.ts        0001-initial
    shin-godzilla.ts  0002-shin-godzilla
    routes.ts         0003-routes（巡礼コースの見本）

src/lib/intake/       調査結果の受け入れ
  schema.ts           受け取る JSON の形（zod）
  check.ts            座標の引き直しと点検
  pack.ts             通ったものをデータパックに起こす
```

新しい作品を足す手順:

1. `packs/` に `DataPack` を1つ書く（`id` は既存と重複しない連番にする）
2. `index.ts` の `PACKS` に加える
3. `git pull` して再起動するだけ。差分だけが入る

適用済みのパックは `data_packs` テーブルに記録されます。守っていること:

- **利用者が編集した記事は上書きしない。** 同じ名前の場所がすでにあれば、
  その項目には触れず、新しいシーンだけを結びつけます
- 何度実行しても増えない（作品は slug、シーンは本文、比定は組み合わせ、
  票といいねは主キーで重複を防ぐ）
- パックの仕組みを入れる前からある DB は、最初のパックを適用済みとして
  記録してから続きを流します（二重投入されません）

```bash
npm run build && npm start   # 本番ビルド
```

## Vercel + Supabase に公開する

SQLite をやめて PostgreSQL にしてあるのは、Vercel のようなサーバーレス環境では
**ファイルに書いても次のリクエストに残らない**ためです。画像も同じ理由で
Supabase Storage に置きます。

### 1. Supabase 側

1. プロジェクトを作る（リージョンは Tokyo が近い）
2. **Project Settings → Database → Connection string → Transaction pooler**
   の文字列を控える（ポート **6543** のほう。サーバーレスから繋ぐのでこちらを使う）
3. **Storage** で `uploads` という名前のバケットを作り、**Public** にする
4. **Project Settings → API** から `Project URL` と `service_role` キーを控える

### 2. 手元からデータを入れる

```bash
DATABASE_URL='postgresql://...pooler.supabase.com:6543/postgres' npm run db:setup
```

スキーマ作成とサンプルデータの投入がされます。何度実行しても増えません。

### 3. Vercel 側

GitHub リポジトリを Import し、環境変数を設定して Deploy するだけです
（ビルド設定は既定のままで動きます）。

| 変数 | 値 |
| --- | --- |
| `DATABASE_URL` | 手順1で控えた接続文字列 |
| `SUPABASE_URL` | Project URL |
| `SUPABASE_SERVICE_ROLE_KEY` | service_role キー（**公開しないこと**） |
| `SUPABASE_STORAGE_BUCKET` | `uploads` |
| `SEICHI_ADMINS` | 任意。管理者のIDをカンマ区切りで。削除の権限が付く |
| `SEICHI_CONTACT` | 任意。地名検索で外部に名乗る連絡先 |

`.env.example` に同じものを並べてあります。

### 補足

- 手順2を飛ばしても、最初のアクセス時にアプリ自身がスキーマとデータを作ります
  （`pg_advisory_xact_lock` を取るので、同時に複数のインスタンスが起動しても
  二重には入りません）。ただし最初の1リクエストが遅くなるので、
  先に流しておくことを勧めます
- `service_role` キーはサーバー側でしか使いません。`NEXT_PUBLIC_` を付けないこと
- 作品を足したときは、`npm run db:setup` を本番の `DATABASE_URL` に対して
  もう一度流せば、差分だけが入ります

## データモデル

```
PostgreSQL

places（場所＝項目）
  ├ place_revisions（版の履歴）      … 編集のたびに編集後の状態を1件積む
  ├ place_likes（いいね）
  ├ visits（訪問の記録）             … 1人1場所1件。踏破率と足跡の元
  ├ route_stops（コースの停留点）─→ routes（巡礼コース）
  └ identifications（結びつけ）
       ├─ passages（シーン）→ works（作品）   画像・キャプション・出典を持つ
       │    └ passage_revisions（版の履歴）   … シーンも共同編集できる
       ├─ votes（賛成・反対）                 … 異説が出たときだけ効く
       └─ comments（議論）
```

区間距離・所要・踏破率は保存せず、停留点の座標と `visits` から毎回求めています
（場所の座標が直れば、コースの距離もひとりでに直る）。

`users.is_admin` が削除の権限、`users.is_anon` が名乗らずに書いた人の目印、
`deletions` が削除の記録です。`deletions` はどこにも外部キーを張っていません
（消した先はもう無いため）。
